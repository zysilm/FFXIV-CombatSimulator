# 重构方案（分支 `refactor/architecture`）

状态：方案稿（2026-11-14），等用户确认后开工。依据是两份只读调查（布娃娃抽库、插件侧架构），要点记在 [PROJECT_LOG.md](PROJECT_LOG.md) §6。本文件是这次重构的唯一依据；阶段有变化就改这里。

## 1. 目标与约束（用户裁决，2026-11-14）

- **目标**：把布娃娃及相关物理中不针对 FFXIV 骨骼的部分抽成独立的公开库，插件只引用这个库；抽的同时把架构理清楚。库先只面向 .NET。
- **行为必须完全一致**。新功能和行为变更不混进重构提交；确实要变的，单独提交并先问用户。
- 插件侧架构由协调者设计（本文件 §4）。
- 不重写：小步搬移，每一步都能编译、都过验证。

## 2. “行为一致”怎么验证

游戏里的结果本身不可重复（每帧步数取决于帧率，另有按耗时提前跳出、后台拟合超时回退、无种子的随机数）。所以一致性定义为：**同一份录制的输入，重构前后的输出逐位相同**（同一台机器、同一运行时、同一 Bepu 版本）。

| 轨道 | 金标准 | 游戏内补充 |
| --- | --- | --- |
| 布娃娃库 | 在游戏里录下一次布娃娃的全部输入（骨架、姿态、网格、地面查询的应答、设置、每帧 dt）和输出（每步全部刚体位姿、每帧写回的骨骼），离线回放逐位比对 | 用户看手感；`FrameCost:` 行 |
| 插件战斗 / AI | 固定种子的离线决策回放（`Tests/CombatReplay`），逐帧比对目标、动作、MP、冷却 | 日志统计对比基线：`Allies (…)`、`Enemies (…)`、`Targets:`、`Rescue:`、`War:`、`Crowd:` |

为此要先把时钟和随机源改成可注入（默认值不变）。

## 3. 轨道 A：布娃娃库

`Animation/` 共约 3.5 万行：已不依赖游戏、可原样搬的 35 个文件约 5,000 行；通用逻辑夹着游戏调用的约 24,500 行（主类 `RagdollController` 及其 partial、`WeaponDropController`、部件分离控制器）；绑定游戏文件格式的约 900 行；必须留在插件的集成代码约 1,000 行；动画播放约 3,900 行不在范围。

库与游戏之间的接口（P2 引入）：

| 接口 | 作用 |
| --- | --- |
| `ISkeletonPose` | 骨骼数、名字、父子关系、参考姿态；模型空间读写；附属子骨架 |
| `IWorldQuery` | 射线、按包围盒采集三角形、找水面 |
| `IMeshSource` | 库不读模型文件，只收中性的顶点 / 索引 / 骨权重 |
| `IRagdollActor` | 身份、朝向、是否主要角色（质量档位）、可选回调（冻结动画、设置渲染根） |
| `RagdollSettings` | 激活时的设置快照（现用 34 个配置属性），加少量实时开关 |
| `IRagdollLog`、`IColliderActorProvider` | 日志；附近会撞到尸体的角色 |

库只暴露 `Step(dt)` 和 `WritePose(pose)`；坐标约定 Y 向上、单位米，换算由适配器负责。FFXIV 的骨骼表、关节限位、体型比例变成一份 profile 数据，由插件提供。

| 阶段 | 内容 | 风险 | 验证 | 量 |
| --- | --- | --- | --- | --- |
| A0 | 录制：在现有代码的接缝旁加只读录制（斜杠命令开关，不进界面），用旧代码录下输入和输出；验证双线程路径和“游戏内录、离线放”能否逐位对上 | 低 | 录制本身就是金标准 | 中 |
| A1 | 新建库项目，把 35 个已纯净的文件原样搬进去（命名空间不变） | 零 | 编译；现有离线测试输出逐字节相同 | 小 |
| A2 | 在插件内引入上表接口，游戏侧写成适配器；模型文件解析、防剔除跟随、隐藏肢体挪到适配侧；注入时钟和随机数 | 中 | 回放逐位相同 | 大 |
| A3 | 骨骼表、关节限位、角色推断、密度、拟合目标改成 profile 数据；表外骨名改为按解剖角色判断 | 低–中 | 回放逐位相同 | 中 |
| A4 | 核心类搬进库，插件留同签名薄壳；主类里的 partial 扩展点改成公开的扩展点接口 | 高 | 回放（所有构建配置都要过）+ 游戏内 | 大 |
| A5 | 掉落武器、部件分离中的物理部分拆出 | 高 | 为它们另录一份 | 大 |
| A6（可选） | 库内把大类拆成组件（建骨、关节、地面、水、头发、抓取…） | 中 | 回放 | 大 |

不进库的：渲染钩子、游戏碰撞场景遍历、几何采集、防剔除跟随、冻结动画、隐藏或克隆模型的渲染手法、调试界面。运行环境：BepuPhysics 2.5.0-beta.22 只有 net8.0 目标，库至少要 .NET 8。

## 4. 轨道 B：插件侧架构

目标形态：

- **一种战斗单位**：`Combatant` 基类，`SimulatedNpc` 和 `CombatCompanion` 继承它，同名成员逐个上提（调用点不用改）。两侧的差异做成策略数据：`ReachPolicy`（射程缩放、近战下限、HP 门槛）、`ActPolicy`（选技能方式、技能令牌、读条与预警、动画锁写法）、`MovePolicy`（速度、转速、踩尸体方式）。玩家不进 AI，只提供只读视图。
- **规则模块**：`IBattleRule`（带空实现的基类），一场战斗挂一组可组合的规则部件。钩子：开始 / 重置 / 每帧、致命一击（死 / 俘 / 处决）、能否处决、有人倒下、主公倒下、接管队友这一帧、敌人目标点、选目标权重乘数、拴绳、强制胜负、结果文案、状态词。现有部件：基础、春秋救人、战国主公倒下、祈祷与守尸、人质、夺尸。新模式 = 一个文件 + 工厂一行 + 下拉一个名字。俘虏、复活、强制胜负这些机制留在引擎，规则只决定何时。
- **组合根**：`Plugin.cs` 按功能拆模块（World、Actors、Combat、Battle、Corpse、Camera、Fighting / EnemyControl、Presentation、Safety / Dev）。断环用的查询抽成 `TargetingService` 和 `CombatRoster`，构造注入；通知类改成 `CombatEvents` 上的类型化事件，订阅顺序集中写在一处；不用事件总线；每帧调用顺序保留为一张显式清单。
- **配置**：不改存储结构（JSON 平铺不变）。`Configuration` 实现若干只读小接口（如 `ICombatAiSettings`、`IBattleRuleSettings`），模块只拿自己那个；界面的读写不动。

必须原样保留的顺序（拆的时候不能动；要动就是行为变更，单独提交并先问用户）：

1. 每帧顺序：队友管理器（含双方选目标、救人、祈祷、队友出手）→ 预警结算 → 导航网格 → 语音 → 人群步进 → 战斗未激活则返回 → 地图敌人 → 引擎 → 待启动布娃娃 → 战争规则 → 敌人 AI → 胜利动作重申 → Fighting 车道重申。
2. 队友在人群步进之前被驱动（战斗外也跑），敌人在之后（只在战斗中）。合并后的控制器保留这两个调用点。
3. 夺尸信息：战争规则写的抢尸名单，敌人 AI 当帧就用，双方选目标到下一帧才看到。
4. `OnOutcomeDecided` 靠赋值串联，依赖胜利庆祝先接线、战争规则后接线。
5. `OnSimulationReset` 的订阅顺序。
6. 含子模块的构建也要编译通过；改公开成员的名字或签名前，由协调者用该构建确认，必要时在插件类上保留同名转发成员。

## 5. 开工顺序

第一批（都不改行为，互不冲突）：**A1**（搬纯净文件）、**A0**（录制）、**B0**（基线日志与可注入随机源）。之后 A2 与 B1–B5 并行；B6、B7 等库落地后再做。

每个阶段一份简报、一个实现者；阶段完成后协调者复查并提交，较大的阶段（A2、A4、A5、B4、B6、B7、B9）加独立审查。

## 6. 调查中发现、不属于重构的问题（各自单独处理）

- `Tests/TargetingSim` 测的是自己的权重副本，不直接证明生产的 `Aggro.cs`；B1 改为链接生产代码后重新对照数字。
- 队友技能在 `potency == 0` 时走带暴击、直击和伤害倍率的路径，敌人不会。是否违反“一套数值”取决于队友技能是否都带 `Potency`，待核实。
- 敌人打队友时，战斗日志仍写“→ You”。
- `HasActiveCompanions` 和 `HasLivingCompanions` 完全相同。
- `Configuration` 被直接传进物理窄相位回调，会在物理工作线程上被读取。
