# 重构方案（分支 `refactor/architecture`）

状态：用户已确认（2026-11-14），按 §5 进行。已完成：A1（`fa89b5a`）、B0（`3e72047`）。依据是两份只读调查（布娃娃抽库、插件侧架构），要点记在 [PROJECT_LOG.md](PROJECT_LOG.md) §6。本文件是这次重构的唯一依据；阶段有变化就改这里。

## 1. 目标与约束（用户裁决，2026-11-14）

- **目标**：把布娃娃及相关物理中不针对 FFXIV 骨骼的部分抽成独立的公开库，插件只引用这个库；抽的同时把架构理清楚。库先只面向 .NET。
- **行为必须完全一致**。新功能和行为变更不混进重构提交；确实要变的，单独提交并先问用户。
- 插件侧架构由协调者设计（本文件 §4）。
- 不重写：小步搬移，每一步都能编译、都过验证。
- **写进用户配置文件的类型不能换程序集**：配置按“类型名, 程序集名”保存（`$type`），类型搬进库后旧配置就读不回来。现存的有 `GuidedCollapseSettings`、`DeathCamPreset`、`RecentNpcEntry`、`EnemyControlGrabProfile`、`EnemyControlGrabPairConfig` 等。库的设置对象（`RagdollSettings`）是运行时快照，不直接序列化。

## 2. “行为一致”怎么验证

游戏里的结果本身不可重复（每帧步数取决于帧率，另有按耗时提前跳出、后台拟合超时回退、无种子的随机数）。所以一致性定义为：**同一份录制的输入，重构前后的输出逐位相同**（同一台机器、同一运行时、同一 Bepu 版本）。

| 轨道 | 金标准 | 游戏内补充 |
| --- | --- | --- |
| 布娃娃库 | 在游戏里录下一次布娃娃的全部输入（骨架、姿态、网格、地面查询的应答、设置、每帧 dt）和输出（每步全部刚体位姿、每帧写回的骨骼），离线回放逐位比对 | 用户看手感；`FrameCost:` 行 |
| 插件战斗 / AI | 固定种子的离线决策回放（`Tests/CombatReplay`），逐帧比对目标、动作、MP、冷却 | 日志统计对比基线：`Allies (…)`、`Enemies (…)`、`Targets:`、`Rescue:`、`War:`、`Crowd:` |

为此要先把时钟和随机源改成可注入（默认值不变）。

### 3.1 A0 录制：录什么、怎么开（已实现，录制器本身待游戏内验证）

**怎么开**：`/combatsim ragdollrec start|stop|status`（不进界面、不加设置，插件每次加载后默认关）。开着的时候，每次布娃娃激活（玩家的布娃娃和每个 NPC 的布娃娃各是一个控制器）各写一个文件，放在插件配置目录的 `ragdoll-rec/` 下，文件名 `<会话时间>-<序号>-<player|npc>-<实体号>.rgdrec`。`status` 显示本次会话写了几个文件、多少字节；`stop` 关闭所有文件。每开、每关一个文件在 `dalamud.log` 里各有一行 `RagdollRec: ...`（路径、渲染帧数、物理帧数、步数、字节数）。录制在激活时开始，录制开启前已经激活的布娃娃不录。

**大小上限（实际值）**：

| 上限 | 值 | 怎么执行 |
| --- | --- | --- |
| 单个文件的字节数 | 512 MiB | 写入器对每条记录检查：会越过上限的那条记录整条不写，之后这个文件只再接受结束记录。文件最大 = 512 MiB + 一条结束记录（不到 1 KiB） |
| 一次会话的总字节数 | 4 GiB | 同一会话的所有文件共用一个计数，同样按记录检查：第一条写不下的记录被拒绝的那一刻起，所有打开的文件都不再接受记录；各控制器在自己的下一个渲染帧发现后，关闭全部打开的文件（日志一行写明原因，每个文件的关闭行也带原因）。会话磁盘占用最大 = 4 GiB + 每个文件一条结束记录（200 个文件合计不到 200 KiB） |
| 一次会话的文件数 | 200 | 开新文件时检查；到了就不再开（日志一行） |
| 单个文件的时长 | 300 秒 | 每个渲染帧检查一次，所以最多超出一帧 |

被上限拒绝的记录之后不会再有别的记录，文件中间不会出现缺口；文件以结束记录收尾，结束原因写明是哪个上限。

**格式**（代码在 `AdvancedRagdoll/Recording/`，纯代码、不依赖游戏；每种记录的字段顺序写在 `RagdollRecordingFormat.cs` 的 `RecordType` 注释里）：文件头 8 字节，之后是一条条带类型和长度的记录；记录内容是带类型标记的值，浮点数按原始 IEEE 位写入，不做任何舍入。记录按事情发生的先后顺序排列。文件被截断时，读到最后一条完整记录为止。

当前格式版本是 **2**（文件头第一个值）。版本 1 是修复前的草稿格式，没有录下“跨激活保留的状态”（见下表“激活时”），不能用来回放；离线工具读到版本 1 的文件会明说这一点。

一条记录写到一半时如果录制代码抛了异常，这条记录不会写进文件，原位置写一条备注 `partial record discarded: <记录类型>`，所以读的一方不会把半条记录当成完整的；关闭文件的日志行会写丢弃了几条。

**录了什么**：

| 时机 | 内容 |
| --- | --- |
| 文件头 | 格式版本、插件版本、是否定义 `DEV_EXPERIMENTAL` / `PUBLIC_BUILD`、BepuPhysics 版本、运行时、操作系统、CPU 架构、SIMD 宽度和指令集、时间、控制器编号、是不是本地玩家、角色地址和实体号（只当不透明编号用） |
| 激活时 | 布娃娃代码读取的全部 34 个配置属性（按名字，完整的值）；`Activate` 的参数；激活前的调用可能留下的状态（待执行的倒地方式、本地断肢名单、轻量碰撞名单、`GrabRigid`）；同一个控制器跨激活保留、`Activate` 和销毁模拟都不清零的状态（见下面“跨激活保留的状态”）；角色的外观数据块、模型编号、朝向、位置；模型类型和种族只在布娃娃代码自己也会去读的条件下才读（已经拿到带模型和 Havok 骨架的骨架），否则记 -1 |

| `InitializePhysics` | 实际用来算初速度的交接样本；全部附属骨架的骨骼名、父子关系、参考姿态和当前姿态；根变换、骨架缩放和绘制对象缩放；应用配置、软组织骨发现和断肢之后实际使用的骨骼定义（每个字段）；每次地面射线和它的应答；采集到的真实地面三角形；附近 NPC 的位置；冻结网格缓存的全部内容（每个区域的顶点和索引）和实际装上的简化网格；凸包拟合的结果，或“没有启动 / 超时改用内置体积 / 失败”；头发网格样本；其他角色碰撞体建立时读到的骨架和姿态（网格模式下是做好的三角形）；额外碰撞角色名单；建成的刚体表；初始化结束时全部刚体的状态 |
| 每个物理帧 | dt、帧开始时的累加器、是否沉睡等状态；写回之前读到的全部附属骨架姿态和根变换；每次世界查询的参数和应答（射线：命中与否、点、法线、材质、三角形；地面三角形；水面）；其他角色的根位置、读到的骨架姿态或变换；武器挥击读到的武器变换；每个从无种子随机源取到的数；依赖墙钟的决定（网格帧提前跳出、简化网格何时装上、行走支撑查询的时间戳）；配置属性的值一旦和激活时不同，就在那一帧开头记一条变更；本帧走了几个子步、是否处于静止、渲染插值系数 |
| 外部调用 | 53 个公开方法：52 个会改变模拟的（外部刚体与外部骨架、抓取、倒地方式、站立支撑、手腕约束、冲量、行走支撑、活体碰撞体、断肢、`Deactivate` 等），加上只读的 `TryResolveGrabAttachment`（它要向游戏读一根骨头的世界位置，包成调用记录后，这条读取记录总有归属：外面直接调时归它自己，`CreateGrabConstraint` 内部调时嵌套在后者之下）。按相对帧的先后顺序记下方法名和全部参数；嵌套层数为 0 的才是真正从外面来的调用，回放只重放这些。`SetDismemberedBones` 是唯一一个调用记录写在调用执行之后的（为了和关闭录制时一样先清表、再遍历调用方给的序列；它内部不产生别的记录）。调用内部向游戏读的东西也记：抓取挂到没有刚体的骨头时读的骨骼世界位置、行走支撑查询读的 NPC 根位置、新增活体碰撞体时读的骨架、是否随抓取携带外部骨架的回调结果 |
| 输出 | 每个固定步之后全部刚体（含运动学刚体和沉睡的）的位置、朝向、线速度、角速度；每帧写回之后全部附属骨架的姿态（物理骨、传播到的非物理骨、脸和头发的附属骨架、缩放写入）；公开方法的返回值；重落地事件 |

连续两帧完全相同的姿态块只记一个“与上一条相同”的标记（动画冻结后读入的姿态每帧相同，静止后的写回也相同）。

**跨激活保留的状态**（同一个控制器第二次及以后的激活，开始时不是全新状态；都写在“激活时”的记录末尾）：

| 状态 | 为什么要录 |
| --- | --- |
| `impactRandomState` | 落地抖动用的随机数发生器，每个控制器一个，从不重置，接着上一次激活往下走 |
| `nextGrabSlotId` | 抓取槽编号，只增不减；编号会作为返回值交给调用方 |
| `externalBodyGeneration` | 每次销毁模拟加一，盖在外部刚体 / 外部骨架的句柄上，用来判断句柄是否过期 |
| `struckThisWindow` | 本次挥击窗口里已经打中过的刚体句柄；销毁模拟时不清，而新模拟的句柄又从 0 开始。开始一次挥击的代码不在公开部分，看不到它是否先清空 |
| `strikeColliderAddresses` | 挥击碰撞体名单；销毁模拟时清，但往里加的代码不在公开部分，不能确认两次激活之间不会写入 |
| `npcTraversalProxyRequests` | 行走代理的请求；`DriveNpcTraversalProxy` 在布娃娃没激活时也会存下请求，要到下次销毁模拟才清 |

逐个查过控制器的全部实例字段（约 260 个）和静态字段，其余的分三类，都不需要另录：每次 `Activate` / `InitializePhysics` / 销毁模拟时重置的；只在本次激活里先写后读的工作状态；跨激活保留但用到时已经录下成品的缓存（冻结网格缓存及其刷新计时、武器接触网格缓存、凸包拟合的进程级缓存、头发网格与平滑后的体表）。只影响日志的（`lastMeshBudgetReport`、`softLeashLogBudget`、`frameCount` 在初始化期间的值、耗时统计）不录。

**没有录的，以及原因**：

- **私有实验模块的代码**（`StepAdditionalPhysics`、`ConfigureAdditionalContact` 两个扩展点和两处 `#if DEV_EXPERIMENTAL`）：不在公开代码里，录不到它读了什么、改了什么。文件头写明构建是否带它；`StepAdditionalPhysics` 是否接管了这一步随每步的刚体状态一起记；挥击窗口计时器和力度每帧记一次观察值。带它的构建录出来的文件，只能和同样带它的构建回放对比。
- **只读查询**（`GetDebugCapsules`、`TryGetExternalBodyPose`、`TryGetBoneCapsule`、`GetBodyWorldPosition`、`NearestBodyDistance`、`CollectCorpseTraversalSlots`、`TryPreviewNpcTraversalRootHeight`、`TryGetWalkableSurfaceHeight`、`TryGetNpcTraversalProxyRoot`、`TryGetCharacterSurface`、`CollectJointLimitStress` 等）：不改变模拟。其中 `TryPreviewNpcTraversalRootHeight` 会读 NPC 的根位置，这条读取记录用单独的来源标记 `TraversalPreviewRoot`（6），和会改变模拟的 `TryGetNpcTraversalRootHeight` 的 `TraversalRoot`（5）区分开；回放遇到 6 直接跳过。没有把它包成调用记录，是因为群体移动每帧会调它上百次。
- **原始模型文件、Penumbra 查询、种族变形文件**：只录做好的成品（网格缓存、拟合结果、骨骼定义、头发样本、三角形），不录原料。A2 把读取模型挪到适配侧，回放从成品开始。
- **嵌入的数据文件**（倒地方式、体表 profile）：随插件版本固定，文件头里有版本。
- **活着时的头发物理**（玩家没死时头发的模拟，含它自己的地面射线）：不属于一次布娃娃激活。布娃娃期间头发的输入（附属骨架姿态、头发网格、身体表面缓存）都录了；头发解算器自身的状态不单独输出，只能从写回的头发骨骼看出来。
- **掉落武器**（`WeaponDropController`，有自己的模拟）：留给 A5 另录一份。它往布娃娃模拟里挂、摘武器刚体的两个调用录了。
- **物理工作线程上的回调**：不在回调里录制（线程间的先后顺序不确定）。回调读到的配置值按帧记变更。
- **写给游戏的东西**（防剔除跟随的位置、动画速度）：不是模拟的输入。它们造成的后果（下一帧骨架根变换的变化）作为输入录了。
- **`Activate` 内部**：录制在 `Activate` 末尾开始，所以它内部启动凸包拟合时读的骨架没录（拟合结果在使用时录）。
- 武器挥击在“没有武器绘制对象”时提前返回，这种帧不记武器样本（没有样本就是没读到）。

**开着录制时，这次模拟本身的已知特性**（录制只观察，但它自己要花时间；下面几点不修，回放和比对时要知道）：

- **网格帧提前跳出更频繁**：子步循环按墙钟计时，录制器写每步刚体状态的时间也算在里面，所以开着录制时“这一帧到此为止”的判断比不录时更容易成立。每次判断的结果都录了，回放照着走。
- **凸包拟合超时更少**：初始化时录制器先写网格缓存，之后才到等待拟合的 150 ms，后台拟合因此多出一点时间，超时改用内置体积的情况比不录时少。结果（完成 / 超时 / 失败）录了。
- **配置变更只在渲染帧开头检测**：一帧中间改的配置，要到下一帧开头才记成变更；同一帧内改了又改回去的看不到。
- **`recDepth`（调用嵌套层数）不是线程安全的**：它是普通的整数加减。从调用方看，包了记录的方法只有两个入口：游戏渲染钩子（`BoneTransformService.RenderDetour` → `OnRenderFrame`）和 `Framework.Update` 上的处理函数（`CombatEngine`、`EnemyControlController`、`Plugin` 等）；公开代码里没有从 `Task.Run` 或物理工作线程调用它们的地方。这两个入口是否在同一个系统线程上，代码里看不出来，要靠游戏内录制的结果确认（层数出现负数或对不上，就是这个问题）。

**离线检查**：`Tests/RagdollRecording`（见该目录 README）。不带参数跑自检（写入、读出逐位相同；截断文件可读；写到一半抛异常的记录不进文件、原位置是一条备注；单文件上限和会话上限按记录执行、文件保持完整；配置监视在没有变化时不分配内存、有变化时只报变化的那一项；“激活时”记录里跨激活保留的状态能读出来，版本 1 的文件报告为缺少它；用真实的 BepuPhysics 小场景录两遍应当相同；改一位能报出第几步、哪个刚体、哪个字段）；给一个文件打印摘要；给两个文件报告第一条不同的输出记录，或“完全相同”。

## 4. 轨道 B：插件侧架构

目标形态：

- **一种战斗单位**：`Combatant` 基类，`SimulatedNpc` 和 `CombatCompanion` 继承它，同名成员逐个上提（调用点不用改）。两侧的差异做成策略数据：`ReachPolicy`（射程缩放、近战下限、HP 门槛）、`ActPolicy`（选技能方式、技能令牌、读条与预警、动画锁写法）、`MovePolicy`（速度、转速、踩尸体方式）。玩家不进 AI，只提供只读视图。
- **规则模块**：`IBattleRule`（带空实现的基类），一场战斗挂一组可组合的规则部件。钩子：开始 / 重置 / 每帧、致命一击（死 / 俘 / 处决）、能否处决、有人倒下、主公倒下、接管队友这一帧、敌人目标点、选目标权重乘数、拴绳、强制胜负、结果文案、状态词。现有部件：基础、春秋救人、战国主公倒下、祈祷与守尸、人质、夺尸。新模式 = 一个文件 + 工厂一行 + 下拉一个名字。俘虏、复活、强制胜负这些机制留在引擎，规则只决定何时。
- **组合根**：`Plugin.cs` 按功能拆模块（World、Actors、Combat、Battle、Corpse、Camera、Fighting / EnemyControl、Presentation、Safety / Dev）。断环用的查询抽成 `TargetingService` 和 `CombatRoster`，构造注入；通知类改成 `CombatEvents` 上的类型化事件，订阅顺序集中写在一处；不用事件总线；每帧调用顺序保留为一张显式清单。
- **配置**：不改存储结构（JSON 平铺不变）。`Configuration` 实现若干只读小接口（如 `ICombatAiSettings`、`IBattleRuleSettings`），模块只拿自己那个；界面的读写不动。
